Next-Concept Modeling on the Hexagon NPU

A 20M-parameter NCM model, trained from scratch on TinyStories, writes a 128-token story in 12 coarse-to-fine steps. This page compares running it on the board's CPU and on its NPU: speed, where the time goes (QNN profiling), how busy the NPU is (Qualcomm sysMon), and how closely the quantized NPU model matches the full-precision one.

From qnn-net-run profiling (4.15 ms NPU compute per generator step, 0.85 ms per decode) and a per-stage timer in the Python runner. Fixed per-call costs (49 ms) were as large as the compute.

What changed
  • Shared buffers (126 → 105 ms): Python loads the QNN runtime in-process and writes inputs straight into DSP-shared memory (rpcmem), so there is no pipe and no copying. The decoder's argmax now runs on the NPU and returns 1,024 token ids instead of a 1 MB logits table, so a decode call takes about 1 ms instead of 6–8 ms.
  • Batching (105 → 100 ms): 4 or 8 stories per NPU call. On its own this saves little, because the NPU's work grows with the batch (about 4.75 ms per story per level).
  • Two batches in flight (100 → 66 ms): while one batch does its sampling on the CPU, the NPU runs the other. The CPU work (about 45 ms per story) now hides behind the NPU work (about 57 ms), which sets the new limit. Both lanes give exactly the same tokens as running them one after the other.

Does quantization change the answers?

For 16 stories, each level's input was given to both the quantized model and the full-precision (fp32) model, and we counted how often they picked the same code. Both always continue from the fp32 choice, so an early difference can't snowball. Level 1 is a single code and always matches.

The batched rebuilds (1, 4 and 8 stories per call, decoder argmax on the NPU) match fp32 just as closely: 88–98% per level and 99.2–99.7% for the decoder, within the run-to-run noise of 16 stories. The 8-bit NPU build was faster in the first version (107 vs 143 ms, unpinned) but loses up to 41 points at level 3. The v68 NPU cannot multiply two 16-bit activation tensors, so the recommended build runs everything at 16 bits except the attention multiplies, which stay at 8.

How these numbers were measured

  • Speed: warm process, 96 stories, two runs per setup, each starting below 60 °C (the board reaches 78–86 °C under load). NPU runs pinned to cores 4–7 with 4 numpy threads; the CPU's best setting is 4 onnxruntime threads and 1 numpy thread on all cores (pinning made the CPU slower: 305 ms at one story per batch). Pinned runs repeat within about 1%.
  • An earlier, unpinned round put the CPU at 808 ms (8 onnxruntime threads) and 586 ms (default settings): thread settings matter as much as the hardware.
  • The DSP hung twice during testing (kernel log: glink "intent request timed out"; every NPU call failed until a reboot). The second time it followed a batch-8, 2-lane run recorded by sysMon whose NPU session took 11 s to close instead of a few ms. Normal runs of the same setup close in 3–7 ms and have not caused a hang; the root cause is unknown.
  • The first-round sysMon capture (23%) was unpinned; pinned to the fast cores, the same first version kept the NPU 45% busy.
  • sysMon was off for speed runs. With sysMon recording, the first NPU version slowed to about 177 ms per story.
  • sysMon reports two active-time figures for the NPU run (2.8 s and 3.6 s of 10 s). Utilisation (23%) is the effective work rate divided by the clock, which these samples reproduce (229 / 958 MHz).
  • Agreement for the CPU INT8 build was checked on the laptop with 8 stories; the NPU builds on the board with 16. NPU-generated stories have not been scored by GPT-2 separately.
  • Each model was trained once; differences between presets come from single runs.
